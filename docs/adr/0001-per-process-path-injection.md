# ADR-0001：每子进程注入 PATH，不使用 nvm use

- 状态：已接受（2026-10-28）
- 相关：GLOSSARY.md「运行时」「注入」「有效运行时」

## 背景

需求是「在同一个程序里跑不同 Node 版本的项目」，并且**多个不同版本的项目要同时运行**。

Windows 上 nvm-windows 的实现方式是：所有版本各占一个目录（`%NVM_HOME%\v18.20.4\`），当前生效的版本由 `%NVM_SYMLINK%`（默认 `C:\Program Files\nodejs`）这个符号链接指向。`nvm use 18` 干的事就是**改这个全局符号链接**。

由此产生两个硬冲突：

1. **全局状态 vs 并发**。项目 A 要 18、项目 B 要 20，同时运行；`nvm use` 是机器级操作，第二次调用会直接把第一次的链接改掉，已在跑的项目虽然进程还活着，但之后任何新起的子进程（比如 `pnpm dev` 内部再拉 `vite`）都会拿到错版本的 Node。
2. **安全护栏 vs 实现需要**。现有代码的 `envProtectedKeys` 明确禁止项目 `env` 覆盖 `PATH` / `NODE_OPTIONS` / `NODE_PATH`——这是对的，它防的是「用户写一份 dev-config.json 就能劫持系统 PATH」。但换运行时本质就是换 PATH 前缀，绕不过去。

## 决定

1. 程序自己解析出一个具体的运行时目录，**为每个子进程单独构造 PATH**：目标版本目录前插到 `os.Environ()` 的 PATH 最前面。全程不调用 `nvm use`，不改任何全局状态。
2. **注入点是代码，不是配置**。`envProtectedKeys` 继续对用户填写的 `env` 生效；程序内部构造的 PATH 走另一条路径，不受该名单限制。两条路径在代码上必须可见地区分开，不能合成一个「合并 env」的入口。
3. 依赖安装（`pnpm install`）与启动命令使用同一个有效运行时。

## 备选方案与放弃原因

- **拼 `nvm use X && <cmd>` 交给 cmd /C**：依赖用户 shell 里的 nvm 初始化状态，且 `nvm use` 的全局副作用会在多项目并发时互相踩。放弃。
- **把命令里的 `node` / `npm` 重写成绝对路径**：`pnpm dev` 这类命令里没有 `node` 字样可重写，`pnpm` 自身才是入口；而 nvm-windows 的每个版本目录里就带着该版本的 `pnpm.cmd`，前插 PATH 一次就能把整条工具链换对。放弃。
- **程序自管 Node 发行包下载**：要处理下载、校验、代理、断点、磁盘占用，收益不抵成本。放弃（复用 nvm-windows）。

## 后果

好处：

- 多项目不同版本真正并发，互不干扰
- 不污染系统全局状态，程序退出后机器保持原样
- 依赖安装与运行时的版本天然一致，避免原生模块 ABI 不匹配（`NODE_MODULE_VERSION` 报错）

代价与需要接受的副作用：

- 需要自己处理 PATH 拼接、目录存在性校验、版本目录缺失时的报错路径
- 与 nvm 的全局状态会**有意不一致**：用户手动 `nvm use 20` 后，指定了 18 的项目仍然跑 18。这是预期行为，不是 bug
- 只覆盖从 nvm-windows 发现的版本；不经 nvm 安装的 Node（如直接 MSI 装的）只能作为「系统默认」使用
